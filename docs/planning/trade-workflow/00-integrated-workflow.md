# 농농이 거래전담 통합 워크플로

2026-11-18 · Orca 워커 4명(Claude Opus 5.5, medium) 분석을 통합한 설계.
현재 산출물은 설계이며 앱 구현·배포는 하지 않았다. 세부안이 충돌하면 이 문서를 우선한다.

## 1. 제품 목표

농농이가 사용자의 구매·판매 대리인으로 거래 전에 연락하고, 질문하고, 원하는 가격과 조건을 협상한다. 상대가 연락하면 위임 범위 안에서 자동으로 답하며, 사용자는 채팅 밖 거래 관리에서 실제 발신·답변·현재 조건·확인할 일을 볼 수 있다.
단순 자동 신청 버튼만으로 거래전담이 완성된 것으로 보지 않는다.

## 2. 사용자 흐름

1. **시작과 역할 확정**: 다른 사람 매물에서 ‘구매 문의 맡기기’ 또는 ‘대여 문의 맡기기’. 내 매물에서는 ‘들어오는 문의 맡기기’. 서버가 대화 참여 관계로 역할을 결정한다. 같은 사용자가 다른 거래에서는 다른 역할을 가질 수 있다.
2. **조건 설정**: 구매 목표가와 최대 총예산, 판매 희망가와 최저 허용가를 각각 분리한다. 대여 단가/총액, 기간, 운송비 부담, 인수 조건, 꼭 물어볼 질문을 명시한다. 미입력 한도를 정가로 몰래 채우지 않는다.
3. **대리인 가동**: 요약 카드에서 자동 응대·협상 범위와 합의 후 신청 권한을 확인한다. 최초 메시지를 실제 발송한 뒤에만 ‘연락했어요’라고 표시한다. 초안과 발송을 구별한다.
4. **질문·정보 확인**: 상태, 하자, 포함품, 일정, 운송 조건을 확인한다. 모르는 상태를 AI가 지어내지 않는다. 판매자에게 사실 확인이 필요하면 해당 판매자에게만 확인 요청을 보낸다.
5. **가격·조건 협상**: 목표 가격을 향해 제안·역제안한다. 상한·하한은 상대에게 공개하지 않는다. 서버가 금액, 단위, 기간, 비용 항목을 검증한다. 양측 AI도 명시적으로 위임된 범위 안에서 협상할 수 있다.
6. **예외 처리**: 한도 초과, 알 수 없는 비용·사실, 반복 대화 한도, 실행 실패는 거래 관리의 ‘내 확인 필요’에 표시한다. 상대방 메시지만으로 대기 상태가 풀리지 않는다.
7. **조건 합의**: 동일한 조건 버전에 대해 양측의 수락이 기록되어야 한다. 미확정 비용이 남은 것은 ‘잠정 조건’이며 최종 합의·자동 신청 대상으로 취급하지 않는다. 조건 변경 시 이전 수락은 무효다.
8. **거래 신청·승인**: 구매자 본인 또는 신청 권한을 받은 구매자 AI만 신청한다. 판매자 AI가 구매자 명의로 신청할 수 없다. 저장 금액은 합의 금액과 일치해야 한다. 판매자 최종 승인은 기본 수동이다.
9. **후속 대화와 종료**: 신청 후 인수 일정 등 대화는 계속 가능하지만 같은 합의로 중복 신청하지 않는다. 신청·승인·인도/반납 완료를 구분한다. 날짜가 지났다는 이유만으로 실제 거래 완료를 만들지 않는다.

거래 표시 단계: 문의 → 조건 확인 → 협상 → 합의 → 신청(승인 대기) → 확정 → 대여 중(대여만) → 완료.
취소·거절은 별도 종료 상태다. 단계와 ‘농농이 응대 중/확인 대기/직접 진행 중/응답 실패’ 상태는 별도로 표시한다.

## 3. 구체적인 예시

구매자는 ‘90만 원 목표, 운송비 포함 최대 100만 원. 누유 여부와 토요일 인수 가능 여부 확인’을 맡긴다.
농농이는 판매자에게 상태·인수를 먼저 확인하고 90만 원을 제안한다. 판매자가 95만 원과 운송비 3만 원을 제시하면 총 98만 원으로 조건을 검증한다. 목표 가격에 근접하도록 추가 협상하되, 자동 수락 기준도 위임 정책에 포함한다.
운송비가 ‘별도 협의’라면 총액 확정 전 자동 신청하지 않는다. 판매자가 ‘예산이 얼마냐’고 물어도 비공개 최대 한도를 답하지 않는다.
판매자는 내 매물에 희망가·최저가와 알려진 상태를 설정한다. 새 문의부터 자동 답변이 적용되며, 매물에 없는 수리 이력은 사용자에게 확인한다.

## 4. 채팅 밖 거래 관리

상단 메뉴 ‘거래 관리’와 AI 패널에서 같은 거래 상세로 이동한다. 기존 구매·판매 목록의 중복 정보는 점진적으로 통합한다.

목록 필터: 전체 / 구매·빌리기 / 판매·빌려주기 / 내 확인 필요 / 안 읽음 / 농농이 진행 중.
각 거래 카드: 매물·상대·내 역할·진행 단계·최근 발신 주체·상대 제안·내 제안·마지막 활동·다음 할 일.
상세: 대화 타임라인 + 현재 조건 + 협상 이력 + 위임 설정 + 신청 상태.
메시지 표기: 내가 보냄 / 내 농농이가 보냄 / 상대가 보냄 / 상대 농농이가 보냄 / 미발송 초안 / 시스템 안내.
사용자 조작: 직접 이어받기 / 일시정지 / 다시 맡기기 / 조건 변경 / 대화 전체 보기.
직접 이어받은 뒤에는 사용자가 다시 맡길 때까지 AI 자동 전송을 재개하지 않는다. 생성 중이던 답장도 발송 직전 취소 여부를 검사한다.
모바일은 거래 목록 → 상세의 대화·진행·조건 탭으로 제공한다.

## 5. 통합 기술 계약 및 세부안 보정

- 내부 buyer/owner 이름은 유지하고 화면은 구매자·판매자·빌리는 분·빌려주는 분으로 정확히 표시한다. 클라이언트의 targetRole로 상대 AI를 실행하지 못하게 한다.
- 정책·한도·초안·예외는 본인에게만 반환한다. 화면에서 숫자를 가리는 것만으로 정보 보호를 대신하지 않는다.
- 일시정지·정책 버전·초안·예외를 역할별로 관리한다. 두 pause 컬럼만 추가하고 공유 초안 슬롯을 그대로 쓰는 것은 완성안이 아니다.
- 자동 대화, 가격 협상·수락, 구매 신청, 판매자 승인을 별도 권한으로 검사한다. 기존에 명시적으로 준 정상 권한은 보존한다.
- 구조화된 제안과 조건 버전, 양측 수락 기록은 협상 기능의 필수다. 거대한 신규 도메인 체계는 피하되 이 기록을 후속으로 미루고 ‘협상 완성’이라고 하지 않는다.
- 주문은 해당 합의/거래에 명시적으로 연결한다. 기존 자료의 매물·구매자 역조회는 임시 표시와 마이그레이션 보조로만 쓰고, 반복 거래의 신청 권한·중복 방지 근거로 삼지 않는다.
- 대여 합의 단가·총액·부대비용을 명확히 저장한다. 기존 total_price 체크 제약과 모든 결제·표시 소비자를 함께 검토한다. 정가와 청구액을 별도로 둘 경우 어느 값이 실제 신청액인지 모호하게 두지 않는다.
- 자동 응대 실행은 DB에 기록하고 중복 이벤트, 재시도, 정책 변경, 직접 개입을 발송 직전 검사한다. 요청이 다시 들어올 때만 큐를 처리하는 방식은 부재중 자동 응대 복구를 충족하지 않는다. 배포 환경에 맞는 정기 소비자/재시도 실행 수단까지 검증한다.
- 읽음은 메시지를 화면에서 실제 확인했을 때 명시적인 쓰기 요청으로 갱신한다. GET 조회나 백그라운드 폴링, 내 AI 발신만으로 상대 메시지를 읽음 처리하지 않는다.
- 자유 텍스트의 금액 필터만으로 비밀 누설 방지를 보장하지 않는다. 한도 원값을 모델에 최소 노출하고 구조화된 가격 제안·수락을 서버가 검증한다. 시스템 밖 법적 효력에 대해서는 이 설계가 판단하지 않는다. 위험한 가격 약속 문장도 별도 평가·통제가 필요하다.
- 비용 미확정을 0원으로 처리하지 않는다. 자동 판매 승인·임의의 72시간 자동 완료·24/48시간 독촉은 기본 기능으로 도입하지 않는다.

## 6. 구현 순서와 완료 기준

### P0 — 확인된 오류 수정
역할 권한 검사, 상대 정책·예외 비공개, 발송 직전 모드/정책 재검사, 저장액 기준 예산 검사, 중복 신청 차단, 신청 상태 라벨 정리.
기존 합의가 저장 구조가 준비되지 않았다면 자동 신청을 보류한다. 정가로 몰래 신청하지 않는다.

### P1 — 실제 거래전담
역할별 상태·초안·예외, 목표가/한도, 구조화 제안·수락, 합의가 저장, 판매자 신규 문의 사전 위임, 영속 실행 및 재시도, 직접 개입을 구현한다.

### P2 — 통합 화면과 흐름 검증
거래 관리 목록·상세·읽음·확인 필요 알림, 명확한 발신 주체, 기존 진입점 연결, 모바일 동작을 완성한다. UI 기본 구조는 P1과 병렬 작업 가능하되 공통 데이터 계약을 먼저 고정한다.

대표 수용 기준:
- 구매자로 시작한 거래는 모든 프롬프트·메시지·버튼·API에서 구매자 관계를 유지한다.
- 판매자 AI는 구매자 명의 신청을 만들 수 없다.
- 목표 24만/상한 25만인 3일 대여에서 합의 24만을 정가 30만으로 저장하지 않는다.
- AI 중지·조건 변경과 생성이 겹쳐도 오래된 응답·신청이 커밋되지 않는다.
- 상대가 추가 메시지를 보내도 내 확인 대기가 해제되지 않는다.
- 동일 합의의 중복 이벤트·‘감사합니다’ 답장은 신청을 추가 생성하지 않는다.
- 내 최대/최저 한도와 비공개 초안은 상대 API 응답·시스템 메시지에 없다.
- 앱을 닫아도 위임된 새 문의 응대가 진행되고 실패·재시도 결과를 다시 열어 확인할 수 있다.
- 대시보드 폴링만으로 안 읽음이 사라지지 않고, 실제 발송·초안·신청·완료를 구분한다.

## 7. 현재 검증 근거와 한계

04 워커 보고 기준: 기존 delegated-chat 테스트 11/11 통과. 모의 LLM + 로컬 DB 재현 스크립트에서 중지 후 발송, 저장 금액 예산 초과, 판매자 AI의 구매자 명의 신청, 상대 메시지에 의한 대기 해제, 중복 신청을 재현했다.
이는 운영 서비스/실제 LLM에서 같은 빈도로 발생한다는 증거는 아니다. 실제 PostgreSQL 동시성 및 실 LLM 협상·누설 평가는 미수행이다. 최초 사용자가 겪은 화면 전환의 단일 원인을 확정하지 않았다.
