## 1. 목표와 범위

브라우저별 데모를 여러 사용자가 같은 매물·거래·대화를 공유하는 영속 웹사이트로 바꾼다. 기존 검색, AI 상담, 기계 사양·호환 추천, 차고, 로그인, 화면 탐색은 유지한다. 데이터 저장 위치만 옮기는 작업이 아니라 소유권, 예약 동시성, 오류 복구까지 서버가 책임지는 전환이다.

이번에 완료한 것은 조사·기획·교차 검증과 별도 로컬 브랜치/작업 공간 준비다. 애플리케이션 수정, DB 생성·변경, 원격 push, Vercel 배포, main 병합은 아직 하지 않았다. 아래 체크리스트는 후속 구현 작업이다.

복구·신규 구현에 포함: 매물 등록/수정/비공개 처리, 모든 회원의 자기 매물 관리, 대여 승인/거절/시작 전 취소, 구매자별 문의함. 현재 main에서 등록 함수는 호출되지 않고 승인 버튼도 없어, 단순 회귀 보존과 구분한다.

제외: 결제·정산, 실시간 소켓/푸시, AI 대화 영구 보관, GPS 거리 기능, 프레임워크 전면 교체, 별도 `agent/` Eve 실험 코드. 판매는 문의 및 판매 상태 관리까지만 다룬다.

## 3. 확정한 제품 규칙

- 검색·상세·추천은 비회원도 사용한다. 등록·대여 요청·채팅·서버 저장은 로그인 후 가능하다. 로그인 유도 시 작성 내용과 돌아갈 화면을 보존한다.
- 모든 회원은 매물 소유자가 될 수 있다. 자기 매물에 대여 요청이나 구매자 문의를 만들 수 없다.
- 비회원 찜·차고는 로컬에 둘 수 있다. 로그인 시 가져오기는 사용자가 명시적으로 선택하며, 공유 브라우저 자료를 자동으로 특정 계정에 귀속시키지 않는다.
- 기존 로컬 매물·요청·채팅은 자동 이관하지 않는다. 원본 키를 보존하고 데모 기록임을 알린다. 운영 데이터가 발견되면 출처·소유권 확인 후 별도 이전표를 만든다.
- 가상 매물은 기본적으로 격리된 Preview에서만 명시적으로 시드한다. 운영에는 가짜 대여 중 표시나 자동 데모 예약을 만들지 않는다. 운영 빈 목록도 정상 화면으로 제공한다.
- 차고는 게시 매물과 독립적이다. 모델 미확인 매물은 일반 검색에 표시할 수 있지만, 호환 판정을 추측하지 않고 확인 필요로 표시한다.
- 기존 본체+작업기 추천은 유지한다. 두 매물은 각각 요청·승인하며 일괄 예약을 보장하지 않는다.

## 4. 기술 구조와 데이터 모델

PostgreSQL + 기존 pg + Better Auth를 유지한다. 공용 DB 풀/트랜잭션 도우미, 기능별 서버 모듈, 공용 API 핸들러, 프런트 데이터 접근 모듈로 구성한다. 형식적인 다중 계층이나 프레임워크 교체는 하지 않는다.

`selectCandidates(message, context, listings)`는 순수 함수로 만들고, 추천/API 진입점에서 목록을 await한다. 모델 사양·호환 규칙은 버전 관리되는 코드에 유지하고 저장 시 model_id를 검증한다. 로컬 개발 서버와 Vercel은 동일한 핸들러를 사용한다.

| 테이블 | 주요 내용·제약 |
|---|---|
| Better Auth 기존 테이블 | 기존 ID·해시·세션 호환 보존. 실제 마이그레이션에서 FK 타입 확인 |
| listings | id, owner_id FK, type, model_id nullable, 제목/사양 요약, crop_ids/operations 배열, 면적 범위, 정수 원화 가격, 지역/상태/점검일, photo_key, is_demo, 시간. 값 범위 CHECK |
| favorites | (user_id, listing_id) 복합 PK/FK |
| owned_machines | id, user_id, model_id, name, is_selected. 사용자당 선택 기계 최대 1대 부분 UNIQUE |
| rental_requests | id, listing_id, requester_id, 시작/종료 DATE, 메모, 일 요금·기간·총액 견적 스냅숏, 상태/결정 시각. 승인 구간 겹침 금지 |
| conversations | id, listing_id, buyer_id. (listing_id,buyer_id) UNIQUE. 매물 소유자는 변경 불가, 대화 참여자 서버 검증 |
| messages | 클라이언트 UUID id, conversation_id, sender_id, 순서 seq, 본문, 시각. 본문 길이 제한 |
| schema_migrations | 버전, 체크섬, 적용 시각 |
| app_meta | 환경 식별, writes_frozen 등 운영 제어 |

사진 1장으로 시작한다. 별도 profiles, 모델 사양 테이블, 사진 갤러리, 작물/작업 연결 테이블, 별도 reservations, 범용 이벤트 시스템은 초기 범위에서 제외한다. 요청 자체가 예약 근거다. FK 삭제 정책은 이력이 사라지지 않도록 제한하며 매물은 소프트 삭제한다. 계정 삭제는 이번 범위에 없고 후속 보존 정책 없이 cascade 삭제하지 않는다.

목록은 기존 DTO를 어댑터로 제공한다. `booked`는 승인 요청의 공개 날짜만, `owner`는 로그인 사용자 기준 계산값이며 권한 근거로 사용하지 않는다. `modelId/specification/demo` 필드와 사진 표시 계약을 유지한다. 개인화 응답은 공용 캐시에 저장하지 않는다. 목록은 사용자 의도와 무관한 잘림이 생기지 않도록 페이지 계약을 정의하고, 추천은 첫 페이지만 대상으로 하지 않는다.

## 5. 거래 상태·동시성·재시도

- 요청: pending → approved/rejected(소유자), pending → cancelled(요청자), approved → cancelled(시작일 전 양쪽). 진행 중 취소·분쟁 처리는 후속 범위다.
- 날짜는 Asia/Seoul의 달력 날짜, 양 끝 포함이다. 오늘 시작 신청/승인은 허용한다. 승인 시 start_date < 오늘이면 거절한다. 승인 건 취소는 오늘 < start_date일 때만 허용한다.
- pending은 재고를 차지하지 않는다. 다른 승인과 겹치는 pending을 자동 거절하지 않고 충돌/기한 경과를 파생 표시한다. 승인 가능한 대기 건만 배지에 집계한다. 완료 여부는 종료일로 파생한다.
- 판매 상태는 open/dealing/done, removed는 비공개 처리다. 대여 신규 신청·승인은 open에서만 허용한다. 활성 승인 예약이 있는 매물의 거래 종류 변경·비공개 처리는 막고, 기존 견적은 가격 수정에도 변하지 않는다.
- 승인/취소/매물 수정은 매물 행 → 요청 행의 동일한 잠금 순서를 지킨다. 소유자·상태·날짜·겹침 검증과 변경은 하나의 트랜잭션이다.
- 우선안: approved 요청에 `EXCLUDE USING gist (listing_id WITH =, daterange(start_date,end_date,'[]') WITH &&)` 적용. btree_gist 지원을 확인한다. 불가하면 모든 예약 쓰기를 매물 행 잠금 + 겹침 조회로 직렬화하고 동일 동시성 테스트를 통과해야 한다.
- 등록·요청·메시지는 클라이언트 생성 UUID와 DB 유일성으로 재시도를 식별한다. 같은 행위자·같은 입력이면 원래 결과 반환, 다르면 데이터 노출 없이 409. 서버는 원래 입력/견적과 비교 가능한 계약을 유지한다. 승인 재전송도 이미 같은 상태면 성공 결과를 돌려준다.
- 사용자 ID, 소유자, 역할, 가격 합계는 클라이언트 입력을 신뢰하지 않는다. 세션과 DB로 계산한다.

## 6. 채팅·사진·프런트 상태

채팅은 열린 대화만 제한된 주기로 폴링한다. 메시지 쓰기는 대화 행 잠금 획득 후 같은 트랜잭션에서 seq 할당·INSERT한다. 조회는 잠금 없이 단일 SELECT로 seq 정렬한다. 최근 N건, after_seq 새 메시지, before_seq 이전 이력을 제공한다. UUID를 시간순 커서로 사용하지 않는다. 대화 생성 경쟁은 UNIQUE와 재조회로 해결한다.

사진은 JPEG/PNG/WebP, 기존 기준 1MB 입력부터 시작한다. 서버 이미지 라이브러리를 도입해 디코딩·픽셀/용량 제한·재인코딩·메타데이터 제거를 수행한다. 구체 패키지와 Vercel 런타임 지원은 구현 시 공식 문서·실배포로 검증한다. 클라이언트 검사는 편의 기능이다.

객체 저장소에는 서버가 정한 매 시도 고유 키로 올리고 DB에는 객체 키만 저장한다. 재시도는 기존 결과를 먼저 확인한다. 실패 시 즉시 정리하되, 정리 실패/프로세스 종료에 대비한 오래된 미참조 객체 대조 명령과 로그를 둔다. removed 매물의 참조도 보존한다. 교체 시 DB 커밋 후 이전 객체를 정리하고, 커밋 결과가 모호하면 참조 확인 전 삭제하지 않는다. 공개 매물 사진 외 비공개 대화 첨부는 이번 범위에 없다.

프런트는 서버 성공 후 화면을 확정한다. 실패·타임아웃·409·세션 만료를 구분하며 거짓 성공 표시를 하지 않는다. 계정 변경 시 사용자 캐시와 진행 요청을 무효화하고 이전 계정의 늦은 응답을 버린다. 공용 필터·화면 취향과 개인 업무 데이터 저장 경계를 분리한다.

| P8 운영 승격 준비 | 최종 diff/변경 계획/잔여 위험 검토, 데이터 백업, 운영 추가 마이그레이션, main 통합 및 배포 절차 준비 | 사용자가 Preview 확인 후 괜찮다고 판단한 뒤 main 병합 |

각 단계는 화면+API+DB+해당 검증이 연결된 단위로 완료한다. 프런트 연동을 마지막에 몰아넣지 않는다. 작업을 작은 커밋으로 나누고 단계별 기존 기능을 계속 확인한다. 계획 문서의 체크리스트를 구현 완료로 오해하지 않는다.

## 8. 필수 검증

- 기존 `npm run check`, `npm run build`: 초기 결과를 기준선으로 기록. 순수 추천 테스트는 명시 fixture, DB 통합은 별도 실제 PostgreSQL로 분리한다. 테스트 기대값을 단순 삭제해 통과시키지 않는다.
- DB/API: FK/값 검증, 트랜잭션 롤백, 겹치는 동시 승인, 당일·경계 날짜, 취소 후 재승인, 등록·요청·메시지 재시도, 권한 A/B/C, 세션 만료, 본문/사진 제한.
- 동시 메시지: 먼저 잠금을 잡은 쓰기가 지연돼도 after_seq 조회에 누락이 없는지 검증.
- 브라우저 자동화 개발 의존성 도입: 두 컨텍스트로 등록→검색/상세→요청→승인→새로고침→대화→시작 전 취소 1개 흐름, 계정 전환+늦은 응답, 네트워크 실패 시 거짓 성공 없음, 세션 만료 후 폼 복구를 추가한다.
- 찜/차고·기준 기계 선택, AI key 없음/실패 fallback, 추천→상세→대여 날짜 전달, 호환 세트의 독립 요청, 판매 문의는 회귀 체크리스트로 확인한다.
- Preview: 운영과 다른 DB/secret/storage, 로그인 쿠키·호스트·Origin, 콜드 스타트 후 영속성, 새 매물의 추천 반영, 이미지 런타임, SQL 마이그레이션 재실행, 운영 DB 비접근을 확인한다.

## 9. 배포·이전·복구

애플리케이션 빌드/요청 안에서 마이그레이션하지 않는다. CI 또는 담당자의 명시 명령으로 대상 확인 → 환경 검증 → 백업 → 마이그레이션 → 검증 → 배포 순서를 적용한다. Better Auth 마이그레이터와 앱 SQL 버전은 구분해 추적한다.

환경 표식이 없다면 최초 1회 명시 init 명령으로 생성한다. 호스트/DB 이름과 의도한 환경을 대조하고, 인증 테이블·기존 데이터가 있는지 먼저 확인한다. 연결 URL 비밀번호는 출력하지 않는다. 이후 표식 없는 DB 또는 불일치 환경에는 migration/seed를 거부한다. 기존 표식을 임의로 덮어쓰지 않는다.

Preview는 운영 DATABASE_URL, BETTER_AUTH_SECRET, 저장소 권한을 상속하지 않는다. Preview 자체의 고정 URL 또는 검증된 배포 호스트 설정을 사용한다. 실제 Vercel 설정과 보호 정책은 아직 확인하지 않았으므로 환경 변수 설정만으로 격리를 달성했다고 주장하지 않는다.

이전은 실제 현황을 확인한 후 추가 전용을 우선한다. 기존 계정 ID·인증 데이터를 보존하고 건수·참조 무결성을 대조한다. Preview에서 복원 리허설을 한 번 수행하며 공급자의 백업 주기/RPO와 복원 시 손실 구간을 기록한다.

첫 실사용 쓰기 전에는 기존 배포로 복귀 가능하다. 새 서버에 거래가 쌓인 뒤 구 데모 배포로 돌리면 거래가 보이지 않아 올바른 복구가 아니다. 첫 출시부터 DB의 writes_frozen을 공용 업무 변경 경로가 확인하도록 하고, 동결 후 전진 수정한다. 이후에는 호환되는 서버 기반 이전 빌드로 복귀할 수 있다. 동결 중 진행 중 트랜잭션 정리와 실제 변경 차단을 확인한 뒤 백업/복구한다. 파괴적 down/drop은 기본 복구 수단으로 사용하지 않는다.

## 10. 구현 전에 확인할 항목 — 설계 이견과 구분

- PostgreSQL 제공자·지역·버전, btree_gist, 연결 풀/접속 한도, 개발·테스트 DB 확보 방법.
- 실제 Better Auth 테이블/ID 타입·버전, 배포 커밋, 운영 사용자·업무 데이터 건수와 소유권.
- Vercel 프로젝트/Preview-Production 변수 스코프, 함수·요청 제한과 현재 Git 연동.
- 객체 저장소 제공자/격리·삭제 권한, 이미지 라이브러리 실행·파일 크기 제한.
- 백업·시점 복구 지원, 실제 RPO, 쓰기 중단과 복원 담당 절차.

이 항목은 코드 검토로 확인할 수 없는 구현 착수 전 조사 항목이다. 제공자·요금제·지원 여부를 추정해 확정하지 않는다.

## 11. 교차 검증 기록과 확정 이유

Codex 조정자와 Claude Fable 5.2가 검토했다. 실행 인자는 `claude --model claude-fable-5-2 --effort high`; Claude는 모델 ID를 내부 확인했고 effort는 실행 인자로 확인했다. 현재 Orca 프로젝트 오른쪽 분리 CLI를 유지한다.

1차: 독립 코드 조사와 D1–D10 비교. 2차: 실질적인 이견 R1–R6만 재검토. 전체 재조사/추가 모델 투입 없이 종료했다.

| 쟁점 | 최종 결정과 근거 |
|---|---|
| 과도한 정규화·계층 | 단순 도메인 모듈과 최소 테이블 채택; 현재 기능에 필요한 관계만 제약 |
| 별도 예약/자동 거절 | 요청 테이블의 승인 구간 제약, 충돌 대기는 유지; 취소 후 재검토 가능 |
| 중복 처리 | 날짜 UNIQUE나 조건부 UPDATE만으로 부족; UUID+행위자/입력 대조 |
| 운영 데이터 없음 단정 | 철회; 실제 배포·DB 재고 확인 전 미검증 |
| 사진 정리/메타데이터 | 서버 재인코딩과 실패 정리·수동 대조 포함; 클라이언트 검증만으로 보장 불가 |
| 메시지 조회 잠금 | Claude의 수정 수용. 쓰기 잠금 후 seq 할당이면 같은 대화의 커밋 순서를 보장하므로 조회 잠금은 불필요 |
| 이전 배포만으로 롤백 | 실쓰기 이후에는 부적합; 첫 릴리스부터 쓰기 동결+전진 수정 |
| 마이그레이션 체크섬/시점 | 체크섬 유지, build/runtime 밖 명시 실행 |
| 검증 범위 | API 검사와 별도로 계정 전환·네트워크·세션 복구 브라우저 검사 유지 |
