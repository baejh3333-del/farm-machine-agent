## 문서 사용법

이 문서는 다음 작업의 시작점이다. 상세 스키마·거래 규칙·완료 기준은 [최종 실행 계획](db-rebuild-plan.md)을 따른다. 이전 검토 문서는 결정의 근거이며 최종 계획과 충돌하면 최종 계획이 우선한다.

## 목표

브라우저 localStorage와 메모리 SQLite에 흩어진 데모 데이터를 PostgreSQL로 통합한다. 회원별 소유권과 거래 권한을 서버에서 검증하고, 여러 사용자와 기기에서 동일한 매물·예약·채팅을 사용할 수 있게 한다. 검색·AI 상담·기계 호환 추천·차고 등 기존 기능은 유지한다.

현재 등록 함수의 호출부와 승인 버튼이 없으므로 매물 등록, 관리, 승인·거절·취소, 사용자별 문의함은 실제 동작하도록 복구한다. 결제, 실시간 알림, 프레임워크 교체는 이번 범위에 포함하지 않는다.

## 구현 작업을 시작하는 방법

1. 작업 폴더의 브랜치와 변경 상태를 확인한다. main이 진행되었다면 차이를 먼저 검토하고 기존 작업을 보존하며 반영한다.
2. 최종 계획을 읽고 P0부터 진행한다. 첫 실행 결과와 기존 실패를 기록한다.
3. 의존성 설치가 필요한 경우 lockfile 기준으로 설치하고 기본 검증을 실행한다.

```powershell
Set-Location 'C:\Users\baejh\orca\workspaces\nongnong\db-rebuild-plan'
git status --short --branch
git log -1 --oneline
npm ci
npm run check
npm run build
```

위 명령은 후속 작업용이며 이 문서를 작성하면서 실행한 것이 아니다. DB 명령은 대상 환경을 확인한 뒤 작성·실행한다. 실제 비밀값을 문서·커밋·로그에 넣지 않는다.

4. P0 결과로 공급자, btree_gist, 풀링, 인증 ID 타입, Vercel 설정, 객체 저장소와 백업 지원을 확인한다. 코드만 보고 운영 데이터가 없다고 단정하지 않는다.
5. 단계별 작은 커밋과 변경 기록을 남긴다. 각 기록에는 수정 이유, 영향받는 흐름, 검증 결과, 미해결 항목을 넣는다.

## 이후 오케스트레이션 방식

기획 검증은 완료했으므로 처음부터 다시 토론하지 않는다. 이후에도 Claude 검토를 사용할 경우 다음처럼 범위를 제한한다.

- 조정자: 구현 범위·파일 소유권·완료 기준 지정, 의존 작업 순서 관리, 결과 통합.
- 구현 담당: 지정 범위만 구현하고 변경 파일·실행한 검사·실패·남은 위험 보고.
- 검토 담당: 변경 diff와 고위험 불변식만 확인. 예약 동시성, 사용자 격리, 데이터 이전, 기존 기능 회귀를 우선한다.
- 합의 항목은 다시 열지 않는다. 코드나 테스트로 반례가 나온 항목만 수정하고 재검증한다.
- 같은 파일을 동시에 수정하지 않는다. 독립 작업만 병렬화한다. 보고 결과를 재실행하는 것은 근거 누락·모순이 있을 때로 제한한다.
- Claude 사용 시 요청 설정 `claude-fable-5-2`, effort `high`를 유지하고 모델 변경은 묵시적으로 대체하지 않는다.
- Orca orchestration 메시지로 작업과 결과를 주고받는다. 워커 실행 후에는 Orca의 결과 알림을 사용하며 반복 폴링하지 않는다.

## 기능이 깨지지 않았다고 판단할 기준

- 기존 check/build 결과 유지. 기대값 삭제로 테스트를 통과시키지 않는다.
- 실제 PostgreSQL에서 동시 승인 두 건 중 정확히 한 건만 성공한다.
- 사용자 A/B/C가 서로의 매물 수정·요청 처리·대화 읽기/쓰기를 할 수 없다.
- 등록→검색→상세→신청→승인→새로고침→채팅→시작 전 취소가 두 브라우저에서 동작한다.
- 계정 전환과 이전 계정의 늦은 응답으로 데이터가 섞이지 않는다.
- 네트워크 실패에 성공 표시가 나오지 않고, 세션 만료 후 작성 중인 폼을 복구할 수 있다.
- 찜·차고·호환 세트·추천 날짜 전달·AI 실패 fallback·판매 문의를 확인한다.
- Preview 콜드 스타트와 다른 브라우저에서도 데이터가 유지된다.

## Preview에서 main으로 넘기는 방법

1. Preview 전용 DB·secret·객체 저장소를 준비하고 운영과 분리되어 있음을 확인한다.
2. 대상 확인 및 환경 검사 후 명시 마이그레이션을 실행한다. build나 일반 API 요청에서 DDL/시드를 실행하지 않는다.
3. 브랜치 배포 후 URL, 배포 커밋, 테스트 계정 사용법, 확인 항목, 알려진 제한을 기록한다.
4. 사용자가 직접 확인할 핵심 흐름을 제공한다. 문제가 나오면 같은 브랜치에서 수정하고 영향을 받는 검사만 다시 한다.
5. 사용자 확인 후 main 반영용 변경 요약·검증 증거·이전 및 복구 절차를 준비한다.
6. 운영 백업과 쓰기 동결 수단을 확인한 뒤 추가 전용 이전 및 병합/배포를 진행한다.
7. 운영 로그인·목록·신청·대화·영속성을 다시 확인한다. 실쓰기 이후 문제가 있으면 구 데모 복귀보다 쓰기 동결 후 수정으로 데이터 정합성을 지킨다.
